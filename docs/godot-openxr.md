# Godot as an OpenXR application on the Monado driver (`ikh xr`)

**Goal.** Exercise the whole chain the way a closed VR application would be exercised:
virtual trackers enter a real OpenXR runtime, a separate application reads them, calibrates
on a T-pose, solves IK, and shows the result on screen as ShaderMotion pixels; the harness
only looks at the screen.

**State.** Working and tested (`tests/test_xr_demo.py`). One command runs it unattended:

```sh
scripts/ikh xr --dataset out/datasets/vsk_walk.json --tracker-set 6pt --ik builtin
scripts/ikh suite --ik renik --readout xr          # every suite entry through this chain (about 5 minutes)
# builtin+openxr+screen / 6pt: body score 16.67 deg (weighted 16.18), end effectors 1.8 cm, 45 frames
# xr: 45 frames off the screen (fbdir), 0.50 s/frame, 0 unstable; ... peak memory demo 372 MB, service 85 MB
# xr: screenshots in out/xr/vsk_walk_builtin_6pt.screen
```

```
dataset frame ─► virtual trackers ─► ikh wire protocol ─► monado-service (ikharness driver)
                                                                  │ OpenXR: head, hands, triggers,
                                                                  │ body trackers (HTCX tracker roles)
                                                                  ▼
                 screen pixels ◄─ ShaderMotion recorder ◄─ IK ◄─ Godot XR demo (T-pose calibration)
                       │
                       ▼  Xvfb framebuffer / X11 screenshot
                 decode slots ─► poses ─► score against the reference
```

## What runs

| Piece | Where | Notes |
|---|---|---|
| `monado-service` | `python/ikharness/service.py` (`MonadoService`) | null compositor, eye buffers 256² by default (`--eye`), guarded |
| XR demo | `godot/harness/xr_demo.gd` | OpenXR session, avatar from the dataset's skeleton, IK adapters of the harness, recorder on screen |
| Tracker roles in the runtime | `monado/patches/0003-htcx-vive-tracker-interaction.patch` | `XR_HTCX_vive_tracker_interaction` for Monado: body trackers as `/user/vive_tracker_htcx/role/<role>` |
| Driver side channel | `godot/harness/driver_client.gd` | GDScript client for `GET_STATE`; fallback for body trackers (`--trackers driver`) |
| Action map | `godot/harness/openxr_action_map.tres` (generated by `godot/tools/make_action_map.gd`) | Index, Touch and simple-controller profiles, Vive tracker profile for ten body roles |
| Display | `python/ikharness/xvfb.py --fbdir` | private Xvfb screen the size of the window, software OpenGL |
| Screen capture | `python/ikharness/screen.py` (`ikh screenshot`) | Xvfb framebuffer file, or `import` / `ffmpeg x11grab` on any X display |
| Orchestration | `python/ikharness/xr.py` (`ikh xr`) | start, wait, calibrate, replay, grab, decode, score |

The demo's window is a spectator view of the avatar with the avatar's ShaderMotion slots in
the three left slot columns (48 of 640 pixels), the layout of a ShaderMotion stream. The
slots are blitted 1:1 from the recorder viewport, so screen pixels equal the shader output.

## Body trackers through OpenXR

Godot (and Unity's OpenXR plugin) read generic trackers through
`XR_HTCX_vive_tracker_interaction`: one top level path per body role
(`/user/vive_tracker_htcx/role/waist`, `.../left_foot`, ...), bound with the Vive tracker
interaction profile. Upstream Monado lists that extension as `ALWAYS_DISABLED`; patch 0003
implements it:

* the 17 roles become subaction paths next to `/user/hand/left` and friends (Monado's
  action code is generated from one macro list, so bindings, action spaces and
  `xrGetCurrentInteractionProfile` follow);
* a generic tracker plays a role when the role's name appears as a whole word in its serial
  or device name (`IKH-TRK-waist`, `Tracker (left_foot)`): there is no role assignment UI as
  in SteamVR, so the name is the assignment;
* `xrEnumerateViveTrackerPathsHTCX` lists the trackers that have a role. The connected
  event is not sent (Godot does not need it).

The driver's trackers declare that they can stand in for the generic Vive tracker device.
In Godot the poses then appear as `XRPositionalTracker`s named after the role path, pose
`default`; the demo reads them from `XRServer`, an `XRNode3D` with that tracker name works
the same. `ikh xr --trackers openxr|driver|auto` chooses the source (`auto`: OpenXR when it
delivers a pose, otherwise the driver's state query); the status line and
`info["body_source"]` say which one was used. Both give the same score.

## Calibration in the demo

Stand in the avatar's rest pose and pull both triggers (rising edge of both `trigger`
values ≥ 0.75). The demo takes the head from the XR camera, the hands from the grip poses,
the body trackers from the driver, and runs `calibration.gd` (the same math as
`python/ikharness/calibration.py`): avatar root (yaw from the hand line, position under the
headset) and one rigid offset per tracker. `ikh xr` performs the gesture remotely: T-pose
poses, one second of holding still, both triggers through the driver's `INPUT` message.
Pulling the triggers again recalibrates.

## Reading the screen

After each frame of tracker poses the orchestrator waits `--min-dwell` (0.3 s), then grabs
the screen until the slot region changed from the previous pose and two grabs 0.1 s apart
agree within 32/255 per channel. Exact equality never happens with iterative solvers: Godot's
FABRIK keeps trembling by a few hundredths of a degree, which is visible in the lowest
ShaderMotion digit only (32/255 there is about 0.1°). Frames that never settle are counted
as `unstable` in the output.

| `--capture` | How | Time per frame (llvmpipe, 2 cores) |
|---|---|---|
| `fbdir` (default) | reads `Xvfb_screen0` (XWD) from the directory given to `Xvfb -fbdir` | 0.5 s |
| `import` | ImageMagick `import -window root` on the demo's display | 0.9 s |
| `ffmpeg` | `ffmpeg -f x11grab` single frame | 1.8 s |

The last two work on any X display, so the same code reads a window of an application we
do not control (`ikh screenshot --display :N --out shot.png`, then `ikh shadermotion decode`).

`--video x264-crf23` additionally records the display with `ffmpeg -f x11grab` during the
replay and decodes the poses a second time from the recording (see `docs/shadermotion.md`
for the codec table); the recording stays in `out/xr/` and is a convenient way to watch a run.

## Run it by hand (to watch it)

```sh
scripts/ikh service &                         # prints the XR_RUNTIME_JSON to export
export XR_RUNTIME_JSON=~/.local/monado-ikharness/share/openxr/1/openxr_monado.json
godot --path godot/harness --xr-mode on --rendering-driver opengl3 -s xr_demo.gd -- \
      --skeleton $PWD/out/datasets/vsk_walk.json --ik builtin \
      --roles head,left_hand,right_hand,waist,left_foot,right_foot &
scripts/ikh replay --dataset out/datasets/vsk_walk.json --tracker-set 6pt --calibrate --dwell 0.5 --loop
```

Without `--roles` the demo calibrates with every device that has a pose at that moment.
`IKH_DEBUG=1` makes it print which tracker poses changed each frame. With a real headset
runtime instead of Monado it runs as a three-point demo (no driver, no body trackers).

## Findings

* **Godot's default OpenXR action map has no Valve Index profile.** Against a runtime whose
  controllers are Index-only, a stock Godot project gets no hand poses and no buttons
  (`/interaction_profiles/none`). The driver's controllers now also emulate Touch and the
  simple controller (the same table Monado's own Index driver uses), and the demo ships an
  action map with all three profiles.
* **Generic trackers did not reach Godot through OpenXR on upstream Monado.** Godot reads
  them through `XR_HTCX_vive_tracker_interaction`, which upstream marks `ALWAYS_DISABLED`;
  Monado offers `XR_MNDX_xdev_space`, which Godot does not know. Patch 0003 adds the
  extension (282 lines); before it the demo used the driver's state query, which remains
  as a fallback.
* **An editor build of Godot writes the default action map into the project** when
  `openxr_action_map.tres` is missing; ours is committed, so runs do not dirty the tree.
* **Pole targets must be in the avatar's frame.** The built-in adapter's elbow/knee hints
  were world-space offsets, which was only right while the skeleton stood at the origin
  facing +Z. After calibration the avatar faces −Z of the stage; the first run scored 19.5°
  instead of 15.2° until the hints followed the skeleton's facing.
* The XR SubViewport (`use_xr = true`) plus a spectator SubViewport plus the recorder
  viewport render at 20 fps with llvmpipe on two cores, 256² eyes, 640×360 window; 370 MB.

## Feedback loop

* `scripts/run_tests.sh xr` (27 s): calibration found through OpenXR (root yaw ±180°, at the
  origin, height ratio 1), screenshots hold slots and the spectator view, the score read off
  the screen matches the in-process recorder readout within 1.5° with head and hips exact,
  and swapped hand trackers (`--perturb hands_swap:1`) score more than 5° worse.
* Same solver, same data, two transports (2026-09-30):

  | Run | in-process (`--readout shadermotion-gpu --calibration tpose`) | through OpenXR and the screen (`--readout xr`) |
  |---|---|---|
  | whole suite, builtin (`ikh suite`) | 20.53° | 20.64° |
  | whole suite, RenIK (`ikh suite`) | 25.56° | 25.56° |
  | walk, builtin, 6pt, 45 frames (body score) | 16.89° | 16.67° |
  | mini walk, RenIK, 6pt (body score) | 18.73° | 18.73° |

  RenIK is deterministic per frame and agrees on all eight suite entries to 0.01°; the
  built-in solver iterates across frames, so settle time shows (the harness reads after
  8 frames, the screen readout waits until the picture rests).
* Look at `out/xr/<run>.screen/frame_00000.png`: an orange avatar on a checkered floor with
  the slot columns on the left. `out/xr/<run>.demo.log` and `.monado.log` hold the logs.
